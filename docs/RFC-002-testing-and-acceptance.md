# RFC-002：测试与验收体系

> 配套 [RFC-001](RFC-001-multi-language.md) · 日期：2026-09-09
> 目标：让「新实现是否正确」成为一个**可自动判定**的问题，而不是靠人肉 review

---

## 1. 为什么现有测试不够

现有 103 个 pytest 用例全部通过（2.69s）。但 §RFC-001 §11/§12 实测发现的 **7 个缺陷，
现有测试一个都没抓到**。原因是覆盖率：

```
现有测试涉及的 adcode:  15 个 / 全部 3271 个  =  0.5%
现有测试涉及的坐标点:    6 个 / 2874 个区县

覆盖的 adcode 全集:
110000 110100 110105 110108 220104 310000 320000 440000
440300 440305 500000 710000 810000 820000 999999
```

即：**测试只覆盖了北京、上海、深圳、长春、南京、港澳台**——全是"标准"区划。
而所有缺陷都在剩下的 99.5% 里：

| 缺陷涉及区划 | 是否被现有测试覆盖 |
|-------------|-----------------|
| 330922 嵊泗县、331083 玉环市（离岛） | ❌ |
| 500152 潼南区、652701 博乐市 | ❌ |
| 150823 乌拉特前旗、330411 秀洲区、331127 景宁县、341623 利辛县、445224 惠来县（层级矛盾） | ❌ |
| 419001 济源市、429021 神农架林区（省直辖县级） | ❌ |

**结论：现有测试的形态（人工挑选典型用例）无法保证正确性。**
需要的是**全量覆盖 + 结构不变量 + 差分对拍**。

---

## 2. 核心陷阱：黄金测试集不能直接从现有实现生成

最自然的做法是「用现有 geopandas 实现跑一遍，把结果存成期望值」。
**这样会把 7 个已知 bug 一起固化成"正确答案"**，新实现修好了 bug 反而测试失败。

对策：引入 **已知差异登记表**（`conformance/known-divergences.yaml`）。

```
黄金集生成流程：
  现有实现输出 ──┐
                ├──> 差异比对 ──> 差异能匹配登记表？──> 是：采用新实现的值
  新实现输出   ──┘                              └──> 否：CI 失败，人工介入
```

**规则：任何未登记的差异一律视为回归。** 新增登记项必须走 PR review。

## 3. 五层测试体系

| 层 | 名称 | 何时跑 | 抓什么 |
|----|------|--------|--------|
| **L0** | 数据管线自检 | 构建 `.gtc` 时 | 数据/格式损坏，不通过则不产出 |
| **L1** | 结构不变量 | 每次 PR，所有语言 | 逻辑自洽性；**不随数据版本失效** |
| **L2** | 黄金测试集 | 每次 PR，所有语言 | 具体取值回归 |
| **L3** | 差分对拍 | Nightly | 未预料的回归 |
| **L4** | 跨语言一致性矩阵 | 每次 PR | 实现间漂移 |
| **L5** | 打包安装冒烟 | 发版前 | 分发形态问题 |

### L0 — 数据管线自检（构建期，产出即校验）

`pipeline/validate.py`，不通过则 `.gtc` 不生成：

1. 计数与 `DATA_VERSION.json` 一致（34 / 363 / 2874）
2. 所有 adcode 为 6 位数字且唯一
3. **每个 district 都能解析出 parent city，覆盖率必须 2874/2874**（RFC-001 §12.2 的教训）
4. 每个区划 bbox 落在中国范围内
5. 网格索引抽样校验：随机 10 万格，实心格的断言与直接几何判定一致
6. 量化前后每个区划代表点偏移 < 5 m
7. 解码 `.gtc` 后重新编码，字节级一致（round-trip）
8. 每个 section 的 CRC32 校验通过

### L1 — 结构不变量（最有价值的一层）

**不依赖任何黄金值，因此数据更新后不会失效。** 所有语言实现都必须通过：

| # | 不变量 | 断言数量 |
|---|--------|---------|
| INV-01 | `reverse(区划代表点)` 必返回该区划本身（自反性） | 2874 |
| INV-02 | `reverse` 结果中 `district.code[:2] == province.code[:2]` | 全部命中点 |
| INV-03 | `reverse` 结果中 city 必是 district 在 META 中登记的 parent | 全部命中点 |
| INV-04 | `is_in_region(区划代表点, 该区划 adcode) == True` | 3271 |
| INV-05 | `lookup_adcode(x).district.code == x` | 2874 |
| INV-06 | `list_regions(lvl)` 的 code 全部唯一，且每个都能被 `get_region` 查到 | 3271 |
| INV-07 | `search(精确名)` 的结果必包含该名的区划 | 3271 |
| INV-08 | 坐标转换往返误差 < 1 m；境外坐标原样返回 | 10000 随机点 |
| INV-09 | 行政树叶子数 == `list_regions("district")` 计数；每个节点 code 可查 | 1 |
| INV-10 | `reverse` 三级齐全时，该路径必存在于行政树中 | 全部命中点 |
| INV-11 | `is_in_china(p) == (reverse(p).province is not None)` | 10000 随机点 |
| INV-12 | `reverse_batch(pts) == [reverse(p) for p in pts]` | 5000 |

> INV-01 ~ INV-05 就能覆盖全部 2874 个区县——这是从 0.5% 到 100% 覆盖率的关键。
> 现有实现在 INV-02 / INV-03 上会**失败**（离岛与层级矛盾），这正是我们要修的。

### L2 — 黄金测试集（语言中立 JSONL）

```
conformance/
├── known-divergences.yaml        # 见 §4
├── reverse.jsonl                 # 分层采样，见下
├── lookup.jsonl                  # 全部 3271 个 adcode
├── search.jsonl                  # 含歧义 / level / 父级过滤 / 无匹配 / 元字符
├── coords.jsonl                  # 坐标转换，带容差
├── containment.jsonl             # is_in_china / is_in_region
└── tree.sha256                   # 行政树规范化 JSON 的哈希
```

`reverse.jsonl` 的分层采样（每条带 `id` 和 `tags`，失败时可定位类别）：

| 分层 | 样本数 | 目的 |
|------|--------|------|
| 每个 district 的代表点 | 2,874 | **保证 100% 区划覆盖** |
| 边界密集采样（沿每条边界内外各偏移 10 m / 100 m） | ~20,000 | 量化误差与 on-edge 规则 |
| 离岛 / 飞地专项 | ~200 | DIV-001 类 |
| 直辖市 / 特别行政区 | ~400 | merged prefix 规则 |
| 省直辖县级行政区（4190/4290/4690/6590） | 30 | DIV 的高发区 |
| 层级矛盾已知点 | 5 | DIV-002 |
| 海域 / 境外 / 极值坐标 | ~500 | 空结果路径 |
| 均匀随机 | 10,000 | 兜底 |

条目格式：

```jsonl
{"id":"rev-00042","tags":["island","province-gap"],"in":{"lat":30.66457,"lng":122.56396},
 "out":{"province":"330000","city":"330900","district":"330922"},"divergence":"DIV-001"}
```

### L3 — 差分对拍（Nightly）

CI 每晚跑 **100 万随机点**，新实现 vs 现有 geopandas 参考实现：

- 每条差异必须能匹配 `known-divergences.yaml` 中的一条规则
- 未匹配的差异数 **必须为 0**，否则构建失败并输出差异样本
- 这是抓「我们没预料到的回归」的网——§12 的 7 个缺陷正是这样发现的

参考实现（geopandas 版）因此**必须长期保留在仓库里**，作为 oracle，不再发布。

### L4 — 跨语言一致性矩阵

```yaml
strategy:
  matrix:
    lang: [python, node, go, rust]
    suite: [invariants, conformance]
```

每个语言实现跑同一份 L1 + L2。**新语言进主仓的准入门槛 = 这两项 100% 通过。**

### L5 — 打包安装冒烟（发版前）

在干净容器里真实安装，跑冒烟测试并断言：

| 断言 | 阈值 |
|------|------|
| `pip show geotool-cn` 的 `Requires:` | **必须为空**（证明 geopandas 已移除） |
| wheel 体积 | < 8 MB |
| 冷启动（子进程，含 import） | < 100 ms |
| `npm install @geotoolcn/core` 的依赖数 | 0 |
| `go build` 在 `CGO_ENABLED=0` 下 | 必须成功 |
| 内存峰值 | < 60 MB |

## 4. 已知差异登记表

以下 7 条为 RFC-001 §11/§12 **实测确认**，是登记表的初始内容：

| ID | 差异 | 类型 | 实测量级 |
|----|------|------|---------|
| **DIV-001** | 离岛的 `province` 从 `None` 变为有值（嵊泗、玉环、潼南、博乐等） | `bugfix` | 8748 点中 ~4 例 |
| **DIV-002** | `city` 与 `district` 不再自相矛盾（乌拉特前旗归巴彦淖尔而非包头等） | `bugfix` | 5 例，均为数据源两层互相矛盾 |
| **DIV-003** | `search(name, province=…)` 不再因几何过滤丢掉离岛（`search("嵊泗县", province="浙江省")` 现返回 0 条） | `bugfix` | 至少 1 例 |
| **DIV-004** | `district` 为 `None` 时 `city` 也置 `None` | `acceptable-loss` | 8622 点中 2 例（**0.023%**） |
| **DIV-005** | `search(fuzzy=True)` 从正则匹配改为纯子串 | `behavior-change` | `search("东.区")` 18 条 → 1 条 |
| **DIV-006** | `list_regions("district")` 改为 adcode 升序 | `behavior-change` | 仅 330113/330114 一对 |
| **DIV-007** | `data_dir` 语义从 GeoJSON 目录改为 `.gtc` 路径 | `api-change` | — |

登记项格式：

```yaml
- id: DIV-001
  title: 离岛的 province 不再为 None
  kind: bugfix                    # bugfix | acceptable-loss | behavior-change | api-change
  reason: >
    省级多边形不覆盖离岛但区县级覆盖。旧实现逐层独立判定，
    返回 province=None 却同时返回 city=舟山市，自相矛盾。
    新实现由 district 的 adcode 反推上级，层级天然自洽。
  affects: [reverse, reverse_batch, lookup_adcode]
  match:                          # 差分对拍时用于匹配差异的规则
    old: {province: null}
    new: {province: "!null"}
    condition: "district != null"
  samples:
    - {lat: 30.66457, lng: 122.56396, district: "330922"}
    - {lat: 28.04746, lng: 121.13337, district: "331083"}
```

`kind` 决定发布策略：
- `bugfix` → CHANGELOG 的 Fixed 段
- `acceptable-loss` / `behavior-change` / `api-change` → **必须**进 `MIGRATION_v3.md`，
  且在 README 显著位置说明

## 5. 验收门禁（Definition of Done）

新实现要能发布，必须**全部**满足：

```
□ L0  数据管线自检          100% 通过，否则 .gtc 不产出
□ L1  结构不变量            100% 通过（12 条 × 所有语言）
□ L2  黄金测试集            100% 通过，差异必须已登记
□ L3  差分对拍 100 万点      未登记差异 = 0
□ L4  跨语言矩阵            所有已发布语言全绿
□ L5  安装冒烟              Requires 为空 / 冷启动 <100ms / 体积达标
□ 现有 103 个 pytest 用例    全绿；若必须失败，需标 xfail 并关联 DIV 编号
□ MIGRATION_v3.md           覆盖所有 kind != bugfix 的登记项
```

> 特别注意最后两项：现有 103 个用例**预计会全部通过**（因为它们只覆盖 0.5% 的标准区划，
> 恰好避开了所有差异点）。**"现有测试全绿"不构成验收依据**，这正是 §1 的教训。

## 6. 数据更新时黄金值怎么办

DataV 数据每年更新，会有区划增删改名，黄金值必然失效。分层应对：

| 层 | 数据更新的影响 | 处理 |
|----|--------------|------|
| L1 结构不变量 | **无影响**，永远成立 | 自动重跑即可 |
| L0 管线自检 | 计数类断言需更新 | 从 `DATA_VERSION.json` 读，自动 |
| L2 黄金集 | 受影响区划的条目失效 | 自动重生成 + **人工 review diff** |
| L3 差分对拍 | 新旧实现用同一份新数据，不受影响 | 自动 |

黄金集重生成流程复用现有的 `DATA_UPDATE_REPORT.md` 机制：

```
1. python pipeline/fetch.py            # 拉新数据
2. python pipeline/build.py            # 产出 .gtc（含 L0 自检）
3. python conformance/regenerate.py    # 重生成黄金集，输出 diff 报告
4. 人工 review diff：新增/删除/改名的区划是否符合官方公告
5. 提交，CI 跑 L1–L5 全套
```

**设计原则：断言尽量用 adcode 而非坐标或序号作主键**，这样区划改名、顺序调整不会导致大面积失效。

## 7. 新增语言的准入清单

任何人想贡献一个新语言实现，必须满足：

```
□ 实现 RFC-001 §4 的完整 API 契约
□ L1 结构不变量 12 条全过
□ L2 黄金测试集 100% 通过
□ 在 .github/workflows 的 L4 矩阵中加入对应 job
□ 该语言生态的惯用测试框架里有基本单元测试（不替代 L1/L2）
□ README 说明安装方式与数据档位选择
```

**不要求**贡献者理解全部设计——跑通 L1+L2 即客观证明实现正确。
这是 RFC-001 §7.2「每语言重写 600 行可接受」得以成立的前提。

## 8. 落地顺序

| 阶段 | 动作 | 为什么是这个顺序 |
|------|------|----------------|
| **P0-a** | 写 `SPEC.md`，钉死 RFC-001 §6.1 的歧义点 | 没有规范就无法判定对错 |
| **P0-b** | 建 `known-divergences.yaml`，录入 7 条实测差异 | 先有登记表，黄金集才能正确生成 |
| **P0-c** | 实现 L1 结构不变量（先跑在**现有实现**上） | 会暴露 INV-02/INV-03 的现存失败——即刻验证登记表 |
| **P0-d** | 生成 L2 黄金集，建 L3 差分对拍 | 此时才有可信的 oracle |
| **P1** | 写 Python v3，用 L0–L3 验收 | 参考实现 |
| **P2+** | 各语言实现，用 L1/L2/L4 验收 | 门槛已客观化 |

**P0-c 是关键检查点**：在现有实现上跑 INV-02/INV-03，应当恰好失败在
DIV-001/DIV-002 涉及的那些点上。若失败集合与登记表不吻合，说明还有未发现的问题。
